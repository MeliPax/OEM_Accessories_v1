System Architecture Overview

The OEM Accessory Pipeline is a modular, multi-stage data processing system that transforms raw OEM Excel files into standardized, vehicle-enriched accessory catalogs. Currently processes 57 sheets per run with 100% success rate.

5-LAYER ARCHITECTURE ├─ LAYER 1: DATA INGESTION (Steps 1-2) │ ├─ Source: OEM Excel files (landing_zone/) │ ├─ Validation & header normalization │ └─ Metadata extraction │ ├─ LAYER 2: DATA TRANSFORMATION (Steps 3-4) │ ├─ Grouping by (Year, Model) │ ├─ Trim column melting │ └─ Cartesian product (Accessories × Trims) │ ├─ LAYER 3: MODEL LOOKUP ENRICHMENT ⭐ CRITICAL (Step 4.5) │ ├─ Keyword extraction & translation │ ├─ Semantic classification │ ├─ Vehicle database search │ └─ Confidence scoring │ ├─ LAYER 4: OUTPUT FILTERING & GENERATION (Step 5) │ ├─ Filter by model_number_status │ ├─ Generate Excel output │ └─ Create DQ reports │ └─ LAYER 5: SUPPORT SYSTEMS ├─ Vehicle database (db_vehicle_models.csv) ├─ OEM configuration (YAML-driven) ├─ Translator & classifier └─ Logging (Pipeline + DQ)

✅ System Status: Production Ready

4 OEM Pipelines Active: Hyundai/Genesis, Mazda, Mitsubishi, Honda (scaffold)

Data Quality: 14 NOT_FOUND cases (40% reduction from v2.4), comprehensive DQ rules

Architecture: Config-driven, cross-OEM patterns, zero hardcoded logic

Honda-Specific Requirements (from raw_note.txt)

Record Types

  • Vehicle Signature Records (Metadata): Model name, year, manufacturer signature. Located at file top before first section marker.
  • Publication Date Records: Two rows at file end (after last section). First has "Publication Date"/"Date de publication", second has date in YYYY-MM-DD format.

Data Row Classification

  • Packages & Kits Section:
    • Parent records: Complete package definitions
    • Child records: Dependent records inheriting parent data
  • Other Sections:
    • Parent records: Complete price data in all columns (Dealer Net, List Price, FRT, Installed Price)
    • Child records: Missing price data, must inherit from parent
    • Single records: Complete data, no child rows

Critical Requirement: Raw Data Output

Auditable raw data sheets must be generated:

Column Description
source_file Excel file this data came from
source_sheet Sheet (EN/FR) within the file
section Section name (Packages, Wheels, Exterior, etc.)
description Part description
part_number Part number value
dealer_net Dealer net price
list_price List price
frt FRT value
installed_price Installed price
comments Additional comments
model Vehicle model name
records_type Type indicator (parent/child/single)

Output Structure: Separate EN_raw_data and FR_raw_data sheets, updated each pipeline run. Enables complete audit trail of source data.

Key Design Principles (Phase 1 Validated)

  • ✅ No hard-coded offsets: All detection via keywords and patterns in config
  • ✅ Language-agnostic: Same detection logic for EN and FR sheets
  • ✅ Scalable structure: Works across all Honda models and years without code changes
  • ✅ Data completeness: Option A+C logic captures both complete and partial records
  • ✅ Configuration-driven: All variations handled in YAML, not Python
