# DQ Report Guide

This guide explains how to read and interpret the data quality reports generated by the OEM Accessory Pipeline.

---

## What is a DQ Report?

A **DQ Report** is a JSON file containing all data quality issues found during pipeline execution. It's generated for each pipeline run and saved to:

```
output/dq_reports/<oem_name>/dq_report_<run_id>_<timestamp>.json
```

**Audience:** Data stewards, business stakeholders, quality reviewers

**Format:** JSON (can be opened in any text editor or parsed by tools)

---

## Report Sheet in Combined Output Excel

Every pipeline run also generates a **single combined Excel file** (`mitsubishi_<run_id>_<timestamp>.xlsx`) that contains model data sheets plus a `_Report` sheet.

#### Section 2: Model Profile
One row per processed model:

#### Section 3: DQ Records
All flagged records with actionable details:

### Using the Report sheet

**For quick triage:**
1. Open the combined Excel file
2. Review the Run Summary: How many warnings? How many sheets processed?
3. Scan Model Profile: Which models have the most issues?
4. Sort/filter DQ Records by Rule: Focus on `non_null_column_rule` issues (excluded from output) or `profitability_rule` (included but needs pricing review)

**For detailed review:**
- Click on a model sheet tab to see the actual data
- Use Part Number and Description columns to locate records in the source file for verification

## DQ Report Structure

Every DQ report has two main sections:

```json
{
  "summary": { ... },
  "records": [ ... ]
}
```

### `summary` section

A high-level overview of issues by sheet and rule type:

```json
"summary": {
  "2026 Outlander": {
    "total_warnings": 6,
    "by_rule": {
      "non_null_column_rule": 2,
      "profitability_rule": 4
    }
  },
  "2026 PHEV": {
    "total_warnings": 4,
    "by_rule": {
      "profitability_rule": 4
    }
  }
}
```

**Use case:** Quickly see which sheets have issues and how many.

### `records` section

Detailed list of every issue found. Each record contains:

```json
{
  "sheet_name": "2026 Outlander",
  "model_name": "2026_outlander",
  "record_index": 42,
  "rule_violated": "non_null_column_rule",
  "issue_description": "Column 'msrp' is null/empty — record excluded from output",
  "record_snapshot": { "part_number": "MZ123456", "msrp": null, ... }
}
```

**Use case:** Investigate individual records and take action.

## Rule Reference

Each issue is tagged with a `rule_violated`. Here's what each rule means and how to respond:

### `non_null_column_rule`

**What it means:** A record has a null or empty value in a required column (part number, price, etc.).

**Example columns affected:** `part_number`, `msrp`, `english_description`, `install_time`

**Output impact:** **Excluded from output.** This record will NOT appear in the final Excel file.

**What to do:**
1. **Check the data:** Is the source Excel file correct, or is the OEM missing information?
2. **Contact the OEM:** If critical data is missing, ask the OEM to provide it.
3. **Update the file:** Once the OEM provides corrected data, re-run the pipeline.

**Example DQ entry:**
```json
{
  "sheet_name": "2026 Eclipse Cross",
  "record_index": 122,
  "rule_violated": "non_null_column_rule",
  "issue_description": "Column 'msrp' is null/empty — record excluded from output",
  "record_snapshot": {
    "part_number": "MZ999999",
    "english_description": "Some part",
    "msrp": null,
    "install_time": 1.5
  }
}
```

---

### `profitability_rule`

**What it means:** A record has a pricing issue: MSRP is less than or equal to DNP (dealer net price), or either value is ≤ 0.

**Math:** Profit = MSRP - DNP. If this is ≤ 0, the margin is zero or negative.

**Output impact:** **Included in output.** The record is still processed and appears in the final Excel, but flagged for review.

**What to do:**
1. **Verify with the OEM:** Confirm the pricing is intentional (loss leader, promotional, etc.).
2. **Update pricing if needed:** If the OEM agrees there's an error, correct it and re-run.
3. **Accept if intentional:** If this is a promotional or special price, you can acknowledge and move forward.

**Example DQ entry:**
```json
{
  "sheet_name": "2026 Outlander",
  "record_index": 15,
  "rule_violated": "profitability_rule",
  "issue_description": "MSRP (50.00) must be greater than DNP (50.00)",
  "record_snapshot": {
    "part_number": "MZ555555",
    "english_description": "Promotional item",
    "msrp": 50.00,
    "dnp": 50.00,
    "install_time": 0.5
  }
}
```

---

### `trim_applicability_rule`

**What it means:** A record applies to zero trim levels. The part is listed, but there's no "X" in any trim column (e.g., ES, SE, LE), so it's unclear which vehicle configurations it fits.

**Output impact:** **Excluded from output.** This record will NOT appear in the final Excel file.

**What to do:**
1. **Check the row:** Is this a header row, subtotal, or junk data that shouldn't be in the file?
2. **Check trim columns:** If it's a real part, verify that trim markers ("X") are present and correctly spelled.
3. **Update the file:** Add the correct trim markers and re-run the pipeline.

**Example DQ entry:**
```json
{
  "sheet_name": "2026 PHEV",
  "record_index": 89,
  "rule_violated": "trim_applicability_rule",
  "issue_description": "Record applies to zero trim levels — excluded from output",
  "record_snapshot": {
    "part_number": "MZ777777",
    "english_description": "Mystery part",
    "es": null,
    "se": null,
    "le": null,
    "sel": null,
    "gt": null
  }
}
```

---

### `trim_candidate_failed_validation`

**What it means:** A column was suspected to be a trim column (found between the "Remarks" and "Photo" boundaries), but its content doesn't look like trim data.

Expected trim columns contain mostly "X" values, blanks, and nulls. If a column has other content (descriptions, numbers, etc.), it fails validation.

**Output impact:** **Trim column is excluded,** but the rest of the sheet processes normally. Other trim columns are still used.

**What to do:**
1. **Review the column:** Check what content is in the flagged column.
2. **Check configuration:** If this is a real trim column for your OEM, the trim boundary rules in the config may need adjustment.
3. **Contact support:** If you believe this is a configuration issue, provide the OEM name and column name.

**Example DQ entry:**
```json
{
  "sheet_name": "2026 Outlander",
  "record_index": -1,
  "rule_violated": "trim_candidate_failed_validation",
  "issue_description": "Column 'mystery_column' failed trim validation — expected_data_rate=5%, unique_values=['description text']",
  "record_snapshot": {
    "column": "mystery_column",
    "expected_data_rate": 5,
    "unique_col_data": ["description text", "more text"]
  }
}
```

## How to Interpret the Summary

Quick checklist:

1. **Total warnings = 0?** ✅ Perfect! No issues found. All records are in the output.

2. **Only `profitability_rule` violations?** ✅ Safe to proceed. Records are in output; pricing should be verified with OEM.

3. **`non_null_column_rule` violations?** ⚠️ Some records were excluded. Check how many:
   - < 5% of records → Minor issue, probably OK to proceed
   - 5–20% of records → Investigate; contact OEM if pattern emerges
   - > 20% of records → Major issue; don't proceed until resolved

4. **`trim_applicability_rule` violations?** ⚠️ Some parts don't fit any trim. Check if these are:
   - Header/junk rows → Can be ignored
   - Real parts → Reupload with correct trim markers

## Using DQ Reports in Your Workflow

### For your first run of an OEM
1. Run the pipeline
2. Review the DQ report summary to understand common issues
3. Check a few `record_snapshot` examples to understand the data quality
4. Decide: proceed or ask OEM for corrections?

### For ongoing updates
1. Keep records of what kinds of issues are typical for each OEM
2. If a new batch has significantly more issues, investigate whether something changed (file format, data source, etc.)
3. Set thresholds: e.g., "We won't process if > 10% of records have profitability issues"

### For auditing
1. Retain DQ reports to show stakeholders what was reviewed
2. Use `record_snapshot` to document specific issues for follow-up
3. Track changes over time: are data quality issues improving or getting worse?

## Example: Reading a DQ Report

Given this DQ report:

```json
{
  "summary": {
    "2026 Outlander": {
      "total_warnings": 6,
      "by_rule": {
        "non_null_column_rule": 2,
        "profitability_rule": 4
      }
    }
  },
  "records": [
    {
      "sheet_name": "2026 Outlander",
      "record_index": 15,
      "rule_violated": "profitability_rule",
      "issue_description": "MSRP (50.00) must be greater than DNP (50.00)"
    },
    {
      "sheet_name": "2026 Outlander",
      "record_index": 42,
      "rule_violated": "non_null_column_rule",
      "issue_description": "Column 'msrp' is null/empty — record excluded from output"
    }
    ...
  ]
}
```

**Summary interpretation:**
- Sheet "2026 Outlander" has 6 issues total
- 2 records are missing MSRP (excluded from output)
- 4 records have pricing problems (included in output, but flagged)

**Actions:**
1. Check if the 2 missing-MSRP records are real parts or junk rows
2. Verify the 4 pricing issues are intentional or ask OEM to correct
3. After fixes, re-run the pipeline

## Troubleshooting: Common Issues

### "I don't see my expected columns in the output"
→ Check the DQ report for `trim_candidate_failed_validation`. A column you expected to be a trim column may have been excluded.

### "Way too many records excluded due to null values"
→ Check if the `non_null_threshold` in the config is too strict (default is 50%). Ask an engineer if this should be adjusted for your OEM.

### "All records excluded? The sheet was skipped?"
→ Check the pipeline log (`.log` file) for FATAL errors. If a required column is completely missing or >50% of all records have nulls, the sheet is skipped entirely (not a DQ issue, a structural problem).

### "Profitability issues but I can't see the actual DNP/MSRP values"
→ Open the `record_snapshot` field in the DQ report record. It contains the full row data including all column values.
