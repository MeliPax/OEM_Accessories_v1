## Update 1: Boundary Detection — Use ALL Required Fields

### Problem

The `_trim_to_data_range()` function only checked for non-empty `part_number` when determining data boundaries. This allowed "tail" rows with part numbers but missing other required fields (english_description, msrp, install_time) to pass the boundary check as "legitimate."

These incomplete rows then:
- Flowed into step 3/4 processing
- Failed non-null column validation
- Generated DQ warnings (`non_null_column_rule` violations)

Example: 2024 Mirage had 40 `non_null_column_rule` DQ warnings for rows that should have been trimmed as tails.

### Solution

Expanded the "legitimate" row definition from:
```python
legit_mask = ~(df[part_col].isna() | (df[part_col].astype(str).str.strip() == ""))
```

To:
```python
legit_mask = pd.Series(True, index=df.index)
for req_col in config["non_null_columns"]:
    col_mask = ~(df[col].isna() | (df[col].astype(str).str.strip() == ""))
    legit_mask = legit_mask & col_mask
```

Now a row is "legitimate" only if it has:
- ✓ part_number (non-empty)
- ✓ english_description (non-empty)
- ✓ msrp (non-empty)
- ✓ install_time (non-empty)

### Files Modified

- `accy_v2/oems/mitsubishi/pipeline/step1_validation.py`
  - Function: `_trim_to_data_range()` (lines 235–282)
  - New logic: iterate all `config["non_null_columns"]` for legit_mask
  - New logging: "dropped X tail rows + Y incomplete rows within range"

### Benefits

- ✅ Cleaner DQ reports (fewer false positives)
- ✅ Fewer records requiring downstream handling

## Update 2: Brochure Handling — Correct Execution Order

### Problem

Brochure records (e.g., `2024MIRBROF`, `2026ECLBROF`) have part numbers, so they were being treated as "legitimate" when `_trim_to_data_range()` scanned for the last row with a part number (`last_idx`).

Timeline:
1. `_trim_to_data_range()` ran first → set `last_idx` to last row with part_number (often a brochure)
2. `_drop_brochure_records()` ran second → removed the brochure

Result: The boundary was set using brochures as anchors, then brochures were removed afterward. Conceptually wrong.

### Solution

Swapped execution order in `step1_validation.py` `run()` function:

**Before:**
```python
working_df = _build_working_df(df_raw)
working_df = _trim_to_data_range(...)       # brochures present
working_df = _drop_brochure_records(...)    # brochures removed after
```

**After:**
```python
working_df = _build_working_df(df_raw)
working_df = _drop_brochure_records(...)    # brochures removed first
working_df = _trim_to_data_range(...)       # boundary set on clean data
```

Now:
1. Brochures removed early
2. `last_idx` correctly identifies the last REAL accessory (not a brochure)
3. Any rows after the last real accessory (including notes, empty rows) are properly detected as "tail"

### Files Modified

- `accy_v2/oems/mitsubishi/pipeline/step1_validation.py`
  - Function: `run()` (lines 35–37)
  - Changed order of two function calls only (no logic changes)

### Results

| Metric | 2026 Eclipse Cross | 2024 Mirage |
|--------|------------------|-----------|
| Boundary before | [0–123] | [0–127] |
| Boundary after | [0–121] | [0–114] |
| Brochures removed | 2 | 2 |
| Tail rows deleted | 0 | 11 |

Logs now show correct sequence:
```
Sheet 'X': dropped 2 brochure record(s)       ← First
Sheet 'X': boundary rows [0–N], dropped M tail/note rows ...  ← Second
```

### Benefits

- ✅ Conceptually correct: "last legitimate" = last real accessory, not brochure
- ✅ Cleaner boundaries: correctly detects all rows after last real part as tail
- ✅ Proper DQ model: brochures removed in Step 1 (structural cleaning), not flagged as failures

## Update 3: Trim Exclusion Keywords Filter

### Problem

Structural category-header columns (CATEGORY, ELECTRONICS, INTERIOR, EXTERIOR, CARGO, GENERAL) appear between the `remarks` and `photo/image` boundaries in Mitsubishi sheets. Because `identify_trim_candidates()` uses position-based detection (every column between those two boundaries becomes a candidate), these category headers were swept in as trim candidates.

They then:
- Failed trim validation (0% X-rate, contained only category values)
- Generated `trim_candidate_failed_validation` DQ warnings
- Cluttered DQ reports with structural noise

Example: 2020 RVR sheet had `category` column failing validation and generating DQ warning.

### Solution

Added early exclusion filter in `step2_header_normalization.py`:

1. **New config key** in `mitsubishi_config.json`:
   ```json
   "trim_exclusion_keywords": ["category", "electronics", "interior", "exterior", "cargo", "general"]
   ```

2. **New filter block** in step2 (after candidate identification, before validation):
   ```python
   exclusion_keywords = [k.lower() for k in config.get("trim_exclusion_keywords", [])]
   if exclusion_keywords:
       excluded = [c for c in candidates if any(k in c.lower() for k in exclusion_keywords)]
       candidates = [c for c in candidates if c not in excluded]
       if excluded:
           pipeline_logger.debug(f"excluded {len(excluded)} category column(s): {excluded}")
   ```

3. **Filtering details:**
   - Substring matching (e.g., "CARGO_ITEMS" excluded if "cargo" in keywords)
   - Case-insensitive
   - Excluded columns never enter `validate_trim_by_datatype()`, preventing any DQ warnings
   - Default-safe: `config.get()` with empty list default; OEMs without key unaffected

### Files Modified

- `accy_v2/oems/mitsubishi/config/mitsubishi_config.json`
  - Added `"trim_exclusion_keywords"` list (line 55)

- `accy_v2/oems/mitsubishi/pipeline/step2_header_normalization.py`
  - Added exclusion filter block (lines 49–57)
  - New log: "excluded X category column(s) from trim candidates: [list]"

### Results

| Metric | 2020 RVR |
|--------|----------|
| Trim candidates before | ['es', 'se', 'es_awc', 'se_awc', 'sel_awc', 'limited_edition_awc', 'gt_awc', 'category'] |
| Trim candidates after | ['es', 'se', 'es_awc', 'se_awc', 'sel_awc', 'limited_edition_awc', 'gt_awc'] |
| DQ warnings before | 7 (4 profitability + 2 model_lookup + **1 trim_validation**) |
| DQ warnings after | 6 (4 profitability + 2 model_lookup) |

Log shows proper sequence:
```
[DEBUG] Trim candidates for '2020 RVR': ['es', 'se', ..., 'category']
[DEBUG] Sheet '2020 RVR': excluded 1 category column(s) from trim candidates: ['category']
[DEBUG] Valid trim cols for '2020 RVR': ['es', 'se', ...]
```

### Benefits

- ✅ Reduced DQ noise: no more spurious `trim_candidate_failed_validation` warnings
- ✅ Early interception: excluded columns never wasted on validation
- ✅ Configurable: easy to add/remove keywords for other OEMs
- ✅ Safe: doesn't affect OEMs without the config key
